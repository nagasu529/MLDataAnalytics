# TVSEP Shocks Module: Data Lineage & Transformation History (2007-2024)

เอกสารฉบับนี้บันทึกประวัติการตรวจสอบย้อนกลับ (Data Lineage) รายละเอียดโครงสร้างข้อมูลดิบ ปัญหาเชิงเทคนิคที่พบในแต่ละระลอกปี (Waves) และแนวทางการเขียนคำสั่งแก้ไข (Data Transformation) เพื่อยุบรวมข้อมูลภัยพิบัติและการรับมือให้เป็น Unbalanced Panel Dataset

---

## 1. ยุคกระดาษดั้งเดิม (PAPI Era: 2007, 2008, 2010, 2011, 2013, 2016, 2017)

### 📊 ลักษณะโครงสร้างข้อมูลดิบ
* **รูปแบบไฟล์:** ตารางแนวแบนเดี่ยว (Flat Table) ในระดับเหตุการณ์ (Event-level) 
* **ระบบตัวแปรบ่งชี้:** ใช้รหัส `QID` และ `hhid` ล็อกรหัสประจำครัวเรือนมาตั้งแต่เริ่มต้น
* **ระบบรหัสภัยพิบัติ:** บันทึกข้อมูลผ่านคอลัมน์มาตรฐานสากลดั้งเดิม `_x31001` ถึง `_x31012`
    * ประเภทภัยพิบัติ: บันทึกในคอลัมน์ `_x31002`
    * มูลค่าความเสียหายหลัก: บันทึกในคอลัมน์ `_x31005` หรือ `_x31005a`
    * ระยะเวลาการฟื้นตัว: บันทึกในคอลัมน์ `_x31012` หรือ `_x31012a`
* **การเก็บข้อมูล Coping:** ใช้ระบบ **"เรียงตามลำดับความสำคัญสูงสุด 3 อันดับ"** โดยครัวเรือนเลือกกิจกรรมตอบสนองมา 3 ข้อ แล้วนำรหัสตัวเลข (1-90) ไปกรอกขนานกันใน 3 คอลัมน์ ได้แก่ `_x31008` (อันดับ 1), `_x31009` (อันดับ 2), และ `_x31010` (อันดับ 3)

### ❌ ปัญหาเชิงเทคนิคที่พบ (Data Bottlenecks)
1.  **Duplicate Variable Labels:** ไฟล์ Stataดิบ (`.dta`) ของบางปีมีปัญหาโครงสร้างป้ายกำกับคอลัมน์ซ้ำกันภายใน ทำให้ Engine โหลดข้อมูลทั่วไปของ Python คอมไพล์ไม่ผ่านและหยุดทำงาน (Crash)
2.  **Wide Priority Format:** โปรแกรมสถิติและแบบจำลอง Regression ไม่สามารถนำตัวแปร 3 อันดับขนานกันไปคำนวณผลกระทบได้ตรง ๆ

### 🛠️ ลอจิกการวิเคราะห์และแก้ไขในสคริปต์
1.  **Binary Mode Override:** ใช้แพ็กเกจ `pyreadstat` เปิดโหมดข้ามการเช็กความซ้ำซ้อนของป้ายกำกับ เพื่อบังคับอ่านค่า Matrix ตัวเลขดิบออกมาให้สำเร็จ
2.  **Row-wise Priority Scanning:** เขียนตรรกะตรวจสอบแนวแถวด้วยคำสั่ง `.isin([code]).any(axis=1)` โดยให้ Python วิ่งกวาดดูทั้ง 3 คอลัมน์พร้อมกัน ถ้ารหัสกิจกรรมนั้น ๆ ปรากฏอยู่ในอันดับ 1 หรือ 2 หรือ 3 จะทำการระเบิดตัวแปรหุ่น (Dummy Variable) ชุดใหม่ในชื่อ `coping_xx` ให้เป็น `1` ทันที หากไม่พบเลยจะบันทึกเป็น `0`

## 2. ยุคเปลี่ยนผ่านระลอกระบบดิจิทัล Wave 8 (2019)

### 📊 ลักษณะโครงสร้างข้อมูลดิบ
* **รูปแบบไฟล์:** `wave-8-2019-shocksclean.dta` เริ่มใช้งานระบบดิจิทัล CAPI ผ่านซอฟต์แวร์ Survey Solutions
* **การเก็บข้อมูล Coping:** ข้อมูลถูกเก็บอยู่ในรูปกลุ่มคอลัมน์กล่องข้อความความสำคัญแบบ Matrix ได้แก่ `v31108a__1` ถึง `v31108a__7`

### ❌ ปัญหาเชิงเทคนิคที่พบ (Data Bottlenecks)
1.  **Missing Global Identifier (QID):** เนื่องจากระบบจัดเก็บเป็นแบบดิจิทัล ตัวแปรระบุเอกลักษณ์ครัวเรือนในตารางภัยพิบัติจึงถูกเปลี่ยนไปผูกกับคอลัมน์ `interview__key` และ `interview__id` ของซอฟต์แวร์ โดย**ไม่มีคอลัมน์ QID ติดมาให้ในตาราง** ส่งผลให้ไม่สามารถเชื่อมโยงเป็น Panel Data ร่วมกับปีอื่น ๆ ได้
2.  **Stata Label Distortions:** คอลัมน์กลุ่ม `v31108a__x` ถูกระบบ Stata ครอบป้ายกำกับประเภท (Categorical Labels) เอาไว้ ทำให้ลูปคำสั่งค้นหาตัวเลขตรง ๆ มองไม่เห็นค่าดั้งเดิม ส่งผลให้ค่าในตารางส่งออกกลายเป็น 0 ทั้งหมด (Data Drop)

### 🛠️ ลอจิกการวิเคราะห์และแก้ไขในสคริปต์
1.  **Crosswalk Integration:** นำตารางทะเบียนประวัติครัวเรือนภาพรวมระดับบุคคล (`TVSEP2019.dta`) เข้ามาทำหน้าที่เป็นตารางจับคู่ (Crosswalk) โดยสั่ง `pd.merge()` ล็อกผ่านคีย์สากล `interview__key` เพื่อดึงรหัส `QID` ดั้งเดิมกลับคืนมาเสียบไว้ที่หัวตาราง
2.  **Numpy Matrix Exact Match:** ปรับเปลี่ยนแนวทางการเข้าถึงตัวแปร โดยแปลงค่ากลุ่มคอลัมน์คำตอบให้เป็น Numpy Array ดิบที่ไร้ป้ายกำกับรบกวน แล้วใช้คำสั่ง `np.any(matrix == code, axis=1)` วิ่งสแกนตรวจจับรหัสกิจกรรม (1-90) บังคับกระจายค่าเข้าสู่คอลัมน์ `coping_xx` ได้สำเร็จร้อยเปอร์เซ็นต์

## 3. ยุคดิจิทัลเต็มรูปแบบแยกตาราง Wave 9 & 10 (2022 และ 2024)

### 📊 ลักษณะโครงสร้างข้อมูลดิบ
* **รูปแบบไฟล์:** ข้อมูลภัยพิบัติถูกแยกโครงสร้างออกจากกันเป็นระบบฐานข้อมูลเชิงสัมพันธ์ (Relational Database) ประกอบด้วย:
    1.  `wave-X-shocks.dta` (ตารางหลัก / Level 1): เก็บรายชื่อครัวเรือนเพื่อคัดกรองว่าเจอภัยพิบัติหรือไม่
    2.  `wave-X-shocks_detail.dta` (ตารางรายละเอียด / Level 2): เก็บพฤติกรรมการรับมือและตัวเงินเสียหาย
* **การเก็บข้อมูล Coping:** บันทึกข้อมูลอยู่ในรูปคอลัมน์ลำดับความสำคัญย้อนกลับไปสไตล์ดั้งเดิมคือ `v31108a__1` ถึง `v31108a__3` แต่บันทึกอยู่ในตารางระดับล่าง (`_detail.dta`) 

### ❌ ปัญหาเชิงเทคนิคที่พบ (Data Bottlenecks)
1.  **Disastrous Data Dropout:** หากโค้ดคำสั่งยึดตารางแม่ (`shocks.dta`) เป็นแกนตั้งต้น ข้อมูลพฤติกรรมการรับมือ (Coping) และมูลค่าความเสียหาย (Cash Loss) จะหลุดหายไปจากระบบทันที เพราะตัวแปรเหล่านั้นถูกเก็บไว้เฉพาะในตารางย่อยระดับล่างเท่านั้น
2.  **Shifting Variable Names:** ชื่อคอลัมน์ประเภทภัยพิบัติเกิดอาการเหลื่อมล้ำกันข้ามระลอกปี เช่น บางปีใช้ `v31102b` ในขณะที่บางปีเปลี่ยนไปสะกดด้วยชื่อ `v31102d`

### 🛠️ ลอจิกการวิเคราะห์และแก้ไขในสคริปต์ [กลยุทธ์ 3-Way Intersect Fix]
เพื่ออุดรอยรั่วข้อมูลขาดหายใน 3 Waves หลังสุด สคริปต์จึงถูกเปลี่ยนกระบวนทัศน์มาใช้วิธีผูกข้อมูลแบบ **"3 ประสาน"** ดังนี้:
1.  **Base Layer Shift:** เปลี่ยนมาใช้ตารางรายละเอียด (`wave-X-shocks_detail.dta`) เป็นแกนตั้งต้นในการรัน Pipeline เสมอ เพื่อรักษาฐานข้อมูลภัยพิบัติที่เกิดขึ้นจริงไว้ให้ครบถ้วนที่สุด
2.  **Parent Intersect Merge:** นำตารางแม่มาเชื่อมโยงผ่านคีย์คู่ขนาน `['interview__key', 'shocks__id']` เพื่อไปดึงเอารหัสประเภทภัยพิบัติ (`v31102b`) ข้ามมาผูกไว้ในตารางย่อยสำเร็จ เพื่อใช้ทำประโยชน์ในการจัดกลุ่มภัยพิบัติภาพรวม (`shocks_Group`)
3.  **Crosswalk & Matrix Extraction:** นำไฟล์ทะเบียนกลางมา Merge ปิดท้ายเพื่อดึงรหัส `QID` กลับเข้าประกบหน้าสุด และใช้ระบบสแกนอาเรย์ Numpy ดึงรหัสพฤติกรรมการรับมือกระจายเข้าล็อกคอลัมน์มาตรฐานเดี่ยว `coping_1` ถึง `coping_90` ได้อย่างสมบูรณ์ ปิดฉากปัญหาข้อมูลหล่นหายระหว่างยุคอย่างเด็ดขาด
